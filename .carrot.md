## Decisions

- **`save` writes to the current directory when there is no repository**, rather
  than refusing. `Repo.root` falls back to `Dir.pwd`; `Repo.in_repo?` reports
  which case applies. The CLI's `ensure_repo!` became `prepare!` and no longer
  raises — it only clears memoized git state.
- The CLI warns when there is no repository, because an uncommitted note does not
  survive a machine swap. Silent success would misrepresent how durable it is.
- A misplaced note is recoverable by moving it. No note is not, and the whole
  point of the tool is that there is one. Offered as "just do it" versus "make
  me pass a flag first"; the first won.
- The use is not limited to switching between *different* agents. A session that
  dies from a power cut or a dropped connection is the identical problem to the
  next session, and that is the case that actually prompted the change.

## Tried and failed

**The blanket substitution rewrote a branch name in another repository.** The
gsub turned a prose reference to `chore/add-carrot-handoff` into
`chore/add-zanoria`, which is not the tool's name and is not a branch that
exists. One occurrence, in this note, and it would have shipped a false claim
about the state of `tinaja-bot` — caught only because the surrounding sentence was
read back after the edit.

A rename substitution cannot distinguish the product's name from a string that
merely contains it. Grepping the result for the *absence* of the old name proves
nothing about whether the new text is true. The defence is to search the diff for
each renamed token **in context**.

**This `sed` has no `-P`, so the negative lookahead had to be Ruby.** The plan
was `sed -P 's/carrot-handoff(?!:(begin|end))/zanoria/g'` to protect the markers.
This build's `sed` rejects `-P`, so the rename ran as a Ruby `gsub` with the same
lookahead. Worth knowing before the next time a rename is planned around a tool
that is not installed — a plan that assumes a flag exists is a plan that fails
late, and the fallback has to carry the same guarantee, not a weaker one.

Nothing failed in the round before this one. The gap was found by checking the
code against a real incident: the session that died mid-task was running in
`~/Developer`, which is not a git repository, so `zanoria save` there would have
raised `not inside a git repository` and written nothing at all.

For the record, the recovery that did work in that incident, in case it is ever
needed again: opencode keeps sessions in SQLite at
`~/.local/share/opencode/opencode.db`. `session_message` holds a JSON `data`
column per message, and querying it by `session_id` recovers the full thread.
Useful as a fallback, not a plan — a schema change or a corrupt table ends it,
and reading it requires already knowing the schema.

**The first push of a new gem could not pass the owner step.** The tag-triggered
Publish run reached `gem push` and the push was refused with the new-gem owner
requirement. The fix — an action release that takes and forwards the owning
account's ID as `owner` — does not exist yet, so the dead end is on the RubyGems
side, not in this repository.

### 2026-10-21, the publish path

Two things are not decided, and neither is urgent.

- **`rake release` has no end-to-end spec.** The guard is specified and the
  workflow's guard was verified by running it, but the task itself — gather
  the facts, build, tag, push — is not exercised anywhere. It would need a
  remote to push a tag to and a network call to `gem list --remote`, and the
  suite deliberately avoids both. A local bare repository as the remote would
  cover the tag push; the network call is the harder half, and the answer may
  be to let the task take the published list from somewhere the spec can
  control.
- **Whether the `release` environment has to exist before the pending trusted
  publisher is registered.** The workflow names it either way, and GitHub
  creates it implicitly at the first release, but the OIDC token only carries
  the environment name if the environment exists when the job starts. If the
  registration names `release` and the token carries nothing, the exchange
  fails with an opaque error. The safe order is to create the environment
  first, which is what the next action says.
