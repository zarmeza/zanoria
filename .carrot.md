## Decisions

- **`save` writes to the current directory when there is no repository**, rather
  than refusing. `Repo.root` falls back to `Dir.pwd`; `Repo.in_repo?` reports
  which case applies. The CLI's `ensure_repo!` became `prepare!` and no longer
  raises — it only clears memoized git state.
- The CLI warns when there is no repository, because an uncommitted note does not
  survive a machine swap. Silent success would misrepresent how durable it is.
- A misplaced note is recoverable by moving it. No note is not, and the whole
  point of the tool is that there is one. Offered as "just do it" versus "make
  me pass a flag first"; the first won.
- The use is not limited to switching between *different* agents. A session that
  dies from a power cut or a dropped connection is the identical problem to the
  next session, and that is the case that actually prompted the change.

### 2026-10-08, init command

- **`init` exists because the wiring was the only real gap.** `save` already
  wrote the note. What nothing did was tell an agent to read it, and no agent
  discovers a file on its own — the README's "Wiring it into an agent" section
  was two lines the reader pasted by hand. `init` writes the note, drops those
  instructions into `AGENTS.md`, and stages both.
- **`init` never overwrites an existing note.** `save` is content and may rewrite
  freely; `init` is scaffolding and may only create. `Tried and failed` is the
  only record of what was tried and exists nowhere else, so the `TASK` argument
  applies only when the note is actually being created. There is a spec asserting
  the file is byte-identical after `init` runs on a filled note.
- **The block is delimited by `<!-- carrot-handoff:begin/end -->` markers.**
  Idempotency is the requirement: `init` gets re-run, and an unmarked append
  stacks a second copy. The markers also let a future version replace the block
  in place instead of asking every repo to hand-edit its own `AGENTS.md`.
- **`init` stages and prints the commit line rather than committing.** Committing
  on someone's behalf manufactures history, and a tool that runs `git commit`
  without being asked will eventually do. Staging is reversible and removes the
  step that actually gets skipped.
- **`--file` is repeatable, defaulting to `AGENTS.md`.** `llama.cpp` here has both
  an `AGENTS.md` and a `CLAUDE.md`, so one-instruction-file was a real limitation
  rather than a hypothetical one. No scan-and-wire-everything: this tool has no
  business editing files it does not own.
- **This repo's own `AGENTS.md` was updated by hand, not by running `init` on
  itself.** Section 2 already covers the handoff loop in more depth than the
  generated block does, so wiring it here would have duplicated it. The command
  table and layout block were edited directly. Dogfooding the *command* is
  covered by the specs and by running it against `tinaja-bot`.
- **`State` now says "Repository has no commits yet" rather than "No git
  repository detected."** Found by running `init` — the first command anyone runs
  in a new repo — against a repo with no commits, which is exactly the case the
  old message got wrong. `branch` and `head` are nil there for the same reason as
  outside a repo, so `Git.root` is what tells them apart. Harmless before, since
  `init` did not exist; actively misleading now.
- **`Wiring` and `Init` are separate modules rather than CLI methods.** `CLI`
  counts ~178 against the 200 `ClassLength` ceiling, and both are independently
  testable. Section 6 already prefers one concern per file.
- **The smoke test asserts `init` idempotency by checksum, running it twice.** A
  behaviour change here would not turn any exit status red. The assertion has to
  be on the bytes, because the bug it guards against — a block that grows a
  blank line per run — passes every status-based check.
- **The README block is generated, not maintained by hand.** It was the second
  copy of the same prose, created by this round, and the recorded lesson from
  the last round is that duplicated text drifts. Two options: delete the copy, or
  make it unfalsifiable. Deleted is worse — a reader deciding whether to run
  `init` is entitled to see what lands in their `AGENTS.md`. So the README's copy
  now sits in a `<!-- block:begin -->` region written by `rake docs:sync`.
- **`Wiring.embed` is shared by the task and the spec, and the spec is a fixed
  point.** `expect(embed(readme)).to eq(readme)` is the whole assertion: change
  `BLOCK`, skip the task, and it goes red. The alternative — a spec comparing
  the README against `BLOCK` with its own substring logic — is a second
  implementation free to be wrong in a new way, which is the drift it was meant
  to detect. One function, two callers.
- **Doc markers are deliberately different strings from wiring markers.** Reusing
  them would give a wired `AGENTS.md` and the documented README a single shared
  region, and neither could then be processed without the other's markers.
- **`docs:sync` is not wired into `rake default`.** A task that silently rewrites
  a tracked file inside the gate hides the fact that the README was stale; the
  spec is supposed to be the thing that tells you.

### 2026-10-08, extra sections

- **Extra sections are rendered, not parsed-and-forgotten.** `save` rewrites the
  whole file, so "never rendered" means "deleted" rather than "hidden". That
  makes writing them back out a correctness requirement, not a nicety: the tool's
  entire reason for existing is that hand-written content survives, and a note
  carrying a heading the tool does not recognize is precisely the case where it
  has no other copy.
- **`Record` keeps the heading as written rather than reconstructing it.** The
  slug is lossy — `normalize` collapses every run of non-alphanumerics to `_` —
  so `Decisions (2026-10-07)` and `Decisions 2026 10 07` are the same key and a
  reconstructed heading would mangle the author's on every save. Storing the
  original costs one hash; the alternative is unrecoverable.
- **Extras render after the canonical sections.** `SECTIONS` order is the
  documented display order (AGENTS.md section 7), so appending preserves it.
  Interleaving would have meant teaching the renderer about position, for no
  reader benefit.
- **The smoke test was corrected, not reverted around.** The obvious move when a
  long-red test blocks a branch is to skip it. That would have hidden the real
  reason `main` was red — a deliberate behaviour change whose test was never
  updated — and left the next agent to rediscover it. Asserting the warning text
  documents the intended contract instead.
- **Dated context goes under `###`, not as its own `##`.** Learned the hard way
  while writing this section: `## State` is regenerated from git on every save, so
  a `###` block that accidentally lands *above* the next `##` heading is treated
  as part of `State` and silently deleted on the next save. Sibling headings
  cannot be used as edit anchors for content that belongs to the previous
  section.

### 2026-10-08, extra sections

**The bug this branch fixes was invisible to every existing spec.** `parse`
kept unrecognized headings, `status` reported them, and both had coverage. What
had no coverage was `render` — nothing ever round-tripped a note containing one
through `save`. `record_spec.rb` asserted the section was *parsed*;
`template_spec.rb` asserted canonical sections rendered *in order*. The gap was
the seam between them.

Two places had to change, and the second was missed on the first attempt.
`Template.render` was the obvious one. But `CLI#save` rebuilds the record with
`Record.new(sections, path: path)` to swap in the task, which silently dropped
the new `headings:` map. A template-only fix would have kept the section while
degrading its heading to a deslugged guess — visible in `status` as
`extra: decisions_2026_10_07`, quietly mangled on every save. The CLI-level spec
is the one that catches that; a template-only spec does not.

**The idempotency spec passes with the bug present.** Worth recording, because
it looks like the strongest of the five. It does not reproduce the bug:
deleting content is itself idempotent, so render→parse→render agrees with
render→parse→render either way. It is a guard against this fix regressing, not
evidence of the bug. The reproduction is the `diff` count in the PR body.

**Hardcoded example counts drift, every time.** `AGENTS.md` and `README.md`
each carried two counts and they disagreed with each other — 50 in the commands
block, 45 in the layout block. Both now read 55, which is correct today and
wrong the next time a spec is added. Neither file generates it. Cheap fix is to
drop the number and let `bundle exec rspec` report it.

**The smoke test was red on `main` before this branch existed**, and the note's
own `Next action` said "confirm CI is green" as though it were. `adeaf6d`
changed `save` outside a repository to warn-and-exit-0; the smoke test still
asserted non-zero. `gh run list --workflow=Smoke --branch main` shows two
consecutive failures, both from the behaviour change, none from anything on this
branch. Worth checking CI history before blaming your own branch for red.

**Do not use a sibling `##` heading as an edit anchor.** A `###` block inserted
directly *above* `## Tried and failed` becomes part of `## State`, and `State` is
regenerated from git on every save — so the block is deleted on the very next
`save`. This is not a bug and not a regression; it is `State` doing the one job
the tool documents for it. It cost a rewrite here, and the same mistake is easy
to repeat on any note that keeps dated context. Anchor edits to unique prose
inside the target section instead.

**A second, quieter version of the same trap: partial edits leave orphans.**
Moving a block by editing its start and end separately left a one-line stub in
the old place and an orphaned fragment inside `Open questions`, and both survived
because `save` only ever rewrites `State` — everything else passes through
untouched. `carrot-handoff status` says `5/5 written` and reports no extras
while the note is visibly wrong, because it counts sections, not their
plausibility. Read the file after a restructure; do not trust the summary.

**Repeated, immediately, while writing this round's own entry.** Anchoring an
edit to a single line of an existing bullet — `- **`save` writes to the current
directory...`, rather` — matched the line's prefix, and the replacement ate the
rest of the sentence. The result was a duplicated `###` heading with orphaned
continuation text beneath it, exactly as described above, thirty lines after
being written down. `git checkout -- .carrot.md` restored it because the note is
committed; that is the whole argument for committing it, demonstrated by the
thing that reads it.

The lesson is not "be careful", it is **anchor to a complete unit.** A whole
paragraph, a whole bullet, a unique closing phrase — never a line that continues
into the next one. Line numbers and single-line anchors are both wrong when the
file shifts underneath, which it does on every `save`.

### 2026-10-08, init command

**`init` was not idempotent, and the bug is one character wide.** The block is
matched by a regex between two markers and reinserted on every run. That regex
stopped at the end marker, so the newline terminating it survived the
substitution and was re-emitted — every run appended one more blank line. Four
runs in, `md5sum` disagreed with the first.

It was caught by end-to-end shell testing before a single spec existed, and it
would have sailed past every spec written afterwards: `init` still exits 0,
still prints `wired`, still writes the same instructions. **Only a byte
comparison catches it** — `expect(lines.count).to eq(23)` would have failed too,
but a `w.include('carrot-handoff load')` would not have noticed at all. The fix
is `[ \t]*\r?\n?` on the end of `BLOCK_RE`, and `wiring_spec.rb` compares
`File.binread` for this reason.

**The general shape: text that round-trips has to be proven byte-stable, not
asserted to contain what it should.** Same reason the smoke test now runs
`init` twice and compares checksums.

**A second idempotency trap, in the other direction.** `Wiring::BLOCK` ended
without a trailing newline, so the block, the marker regex, and the append path
each had their own idea of where the line ended. Fixed in one place
(`Wiring.framed`) after noticing `chomp` was being applied in two different
files for the same reason.

**`--file docs/AGENTS.md` failed *after* already wiring the previous file.**
`init` applied files in order, so a missing parent directory raised on file two
and left file one modified — a half-run that reported nothing about being half.
Two changes: `FileUtils.mkdir_p` the parent, because a path implies its
directory, and `Init` now partitions paths into inside-the-repo and outside
rather than handing `git add` something it will reject.

**`/srv/repo-other` starts with `/srv/repo`.** The first version of the
containment check used `String#start_with?` on the repo root and would have
staged a sibling directory, failing the whole `init`. There is now a spec
constructing exactly that case.

**A spec assertion I wrote was wrong and the code was right.** `expect(record).
to be_empty` on a freshly templated note fails, because `State` is
machine-derived and legitimately full of content — `empty?` asks whether any
section is substantive, and `State` is. The note is not empty; it is *unauthored*.
Asserting the five human sections are prompts says what I meant. Worth recording
because the tempting fix is to make `Record#empty?` ignore `State`, which would
break its documented use for detecting real hand-edited content.

**The `--file` flag also changes what the note's `State` says, and did not
announce it.** `AGENTS.md` shows up in `State` as an uncommitted file, so `init`
makes the very block it writes look like outstanding work on the next `save`.
Accepted, and in fact correct: until it is committed, it is outstanding work.

**Two failed verification attempts, both mine, both worth recording.** Proving
the drift guard works required actually desyncing something, and the first two
attempts desynced nothing:

- `ruby -i -pe 'sub(/^Commit the note.../)'` — the `^` anchor did not match,
  because the line is indented inside the heredoc. The substitution was a no-op,
  the spec passed, and the result looked like a successful negative test. It was
  a vacuous one. **Always assert the mutation landed** (`grep -c` on the
  expected new string) before believing a test that was supposed to go red.
- `gsub("...\`Decisions\`...")` inside double quotes in bash — the backticks ran
  as command substitution. Same failure mode: a green spec meaning nothing.

Both times the tell was the same and cheap to check: `grep -c` for the string I
had just tried to introduce. Worth more than the negative test itself.

**The README block sits in a markdown fence, which nearly broke the marker
placement.** `<!-- block:begin -->` around the *outside* of the
` ```markdown ` fence puts the fence itself inside the replaced region, so
`embed` would write the block unfenced and it would render as a real `##` heading
instead of a preview. The markers go inside the fence. Not obvious, and the
failure would have been visual rather than a test failure.

## Open questions

- **Resolved: the duplicated block.** The README's copy of `Wiring::BLOCK` is
  now generated by `rake docs:sync` and asserted equal by a fixed-point spec.
  Recorded here only so it is not re-raised; see `Decisions`.
- **`init` has no `--dry-run`.** Not asked for, and staging is already the
  reversible part, so the gap is smaller than it sounds. But it writes to a file
  a human wrote, and there is no way to see the diff before doing it except
  running `init` and then `git diff`. Worth revisiting if anyone reports being
  surprised by what landed in their `AGENTS.md`.
- **`rake docs:sync` must be run by hand after editing `BLOCK`.** The spec catches
  the miss, but the workflow depends on remembering. A `rake` hook or a
  pre-commit hook would close it; neither was added, because the miss is loud
  and the alternative is a gate that rewrites files without saying so.
- **`init` stages `AGENTS.md` alongside the note, and stages it even when only
  the note changed.** If someone re-runs `init` after editing their own
  `AGENTS.md`, staging is a no-op, so this is harmless in practice. But the
  report says `Staged AGENTS.md .carrot.md` unconditionally when both are inside
  the repo, whether or not either is new. Accurate enough, slightly overstated.
- **`--file` accepts a path outside the repository and writes it.** Deliberate:
  refusing would be worse than honouring an explicit path, and the file is not
  staged, so the outcome is visible. But "init a repo" now has a code path that
  edits something git does not track, and no argument exists to turn that off.
- `spec/git_spec.rb` needed an explicit `Dir.chdir` for the cwd-fallback case,
  because the surrounding `Dir.mktmpdir` block does not move the process.
  Worth remembering when adding cases: this suite does real `git` shell-outs,
  and stubbing `Git.root` is the exception, not the rule.
- **`status` cannot tell you a note is wrong.** It reports `5/5 written` and no
  extras for a note with a duplicated fragment and a truncated section, because
  it counts non-empty sections rather than checking them. `save` likewise passes
  anything outside `State` through untouched, so a bad hand-edit survives
  indefinitely and looks healthy to both commands. Possible improvement: warn when
  a section's body contains a `###` heading but no `##` context, or when a saved
  note loses a line it previously had. Not trivial, and only worth it if notes
  are hand-edited often enough to matter — which, given this repo, they are.
  Note that this round reproduced the failure by hand and the tooling still
  reported `5/5 written` throughout, which is mild evidence for doing something.
